# 텍스트에서 지식 그래프를 만들기 — 쉬운 해설판

> 이 글은 《Knowledge Graphs and LLMs in Action》 5장 "비정형 데이터에서 도메인 특화 지식 추출하기(Extracting domain-specific knowledge from unstructured data)"의 전체 내용을 빠짐없이 담되, 전문 용어와 개념을 쉬운 한국어와 꼭 필요한 곳의 비유로 풀어 재구성한 해설판입니다. 원문의 모든 문단, 그림, 코드, 표를 그대로 살렸습니다.

이 책의 앞부분에서 세워 둔 큰 그림을 잠깐 떠올려 봅시다. **대규모 언어 모델(LLM)** 은 온갖 것을 다 아는 것처럼 말을 잘하지만 가끔 근거 없이 사실을 지어내기도 하는 달변가 같은 존재였고, **지식 그래프(Knowledge Graph, KG)** 는 검증된 사실만 차곡차곡 정리해 둔 사실 대장 같은 존재였습니다. 이 5장은 그 둘을 실제로 손잡게 하는 첫 번째 실전 장입니다. 바로 "글로만 흩어져 있던 지식을 어떻게 정리된 지식 그래프로 바꿀 것인가"라는 문제를 다룹니다.

## 텍스트에서 지식 그래프 만들기 — 이 파트가 여는 새로운 영역

비정형 텍스트 데이터를 구조화된 지식으로 바꾸는 일은, 똑똑한 시스템을 만드는 여정에서 아주 흥미로운 최전선입니다. 이 파트에서는 **지식 그래프(KG)** 와 **대규모 언어 모델(LLM)** 을 결합해, 글 속에 숨은 지식을 뽑아내고 구조화하고 표현하는 방법을 살펴봅니다. 그리고 이 두 기술이 서로의 약점을 어떻게 보완하면서, 비정형 정보에서 가치를 끌어내는지 보여 줍니다.

왜 이게 중요할까요? 오늘날 기업이 가진 데이터의 **80~90%가 비정형 텍스트**라고 합니다. 이메일, 보고서, 회의록처럼 표로 깔끔하게 정리되지 않은 글들이 그만큼 많다는 뜻입니다. LLM이 등장하면서 이 영역은 완전히 달라졌습니다. 사람 손을 훨씬 덜 빌리고도, 자연어로 쓰인 내용을 이해하고 의미 있는 정보를 뽑아낼 수 있게 되었기 때문입니다. 여기에 전통적인 **자연어 처리(Natural Language Processing, NLP)** 기법과 지식 그래프 기술을 함께 쓰면, 맥락을 이해하면서도 구조화되고 검증 가능한 지식 표현을 유지하는 시스템을 만들 수 있습니다.

이 파트를 이루는 네 개 장이 각각 어떤 이야기를 하는지 미리 짚어 두겠습니다.

- **5장**은 텍스트를 지식 그래프로 바꾸는 과정을 보여 주고, 최신 LLM 기반 방법으로 **개체명 인식(named entity recognition, NER)** 과 **관계 추출(relationship extraction)** 을 하는 법을 소개합니다. 역사 문서에서 구조화된 지식을 뽑아내는 사례 연구가 함께 나옵니다. (지금 읽고 있는 장입니다.)
- **6장**은 문서 처리와 **OCR(광학 문자 인식)** 스캔부터 그래프 분석까지 이어지는 작업 흐름에 집중합니다. 스키마 설계, 데이터 정제, 개체 해소(entity resolution), 네트워크 분석 같은 고급 기법을 보여 줍니다.
- **7장**은 **개체명 중의성 해소(named entity disambiguation, NED)** 를 다룹니다. 개체를 구조화된 지식 베이스에 연결해서, 개념 기반 검색과 지능형 자문 시스템을 가능하게 하는 사례를 소개합니다.
- **8장**은 LLM과 도메인 온톨로지를 결합한 개체명 중의성 해소 방법을 보여 줍니다. LLM에 구조화된 도메인 지식을 더해서, 맥락을 이해하는 중의성 해소를 하는 방식입니다.

여기서 소개하는 기법들은 전통적인 지식 표현과 현대적인 AI 능력이 어떻게 시너지를 내는지를 보여 주며, 지능형 지식 시스템을 만드는 토대를 놓습니다.

## 비정형 데이터에서 도메인 특화 지식 추출하기 — 5장 시작

### 이 장에서 다루는 것 — 미리 보는 목차

이 장에서는 다음 세 가지를 다룹니다.

- 비정형 데이터로부터 지식 그래프 만들기
- 아카이브(기록보관소) 관리의 복잡함: 록펠러 아카이브 센터 사례
- 대규모 언어 모델을 이용해 개체와 관계 추출하기

지금까지 이 책은 표, 지식 베이스처럼 **구조화된 데이터(structured data)** 를 바탕으로 한 지식 그래프를 이야기해 왔습니다. 그런데 비정형 데이터는 어떨까요? 이메일, 채팅, 법령, 연구 논문, 뉴스 기사, 소셜 미디어를 한번 떠올려 보세요. 세상은 정형화되지 않은 형태의 정보와 지식으로 넘쳐 흐릅니다. 이런 데이터 원천을 잘 활용하면 여러분의 비즈니스에 값진 정보를 줄 수 있습니다.

비정형 데이터를 지식으로 바꾸는 작업은 여러 단계로 이루어집니다. 데이터를 받아들여 처리하는 **인제스천(ingestion)**, 다양한 자연어 처리(NLP) 기법, 데이터 보강(enrichment), **머신러닝(machine learning, ML)** 처리, 그리고 실제 응용 프로그램을 떠받치기 위한 데이터 모델링까지 이어집니다. 개념적으로 보면, 이 과정에는 두 가지 큰 도전 과제가 있습니다.

첫째는 **지식 표현(knowledge representation)** 입니다. (이 책 2장에서 다룬 개념입니다.) 지식 표현이란 정보를 어떻게 모델링해서, 컴퓨터(그리고 사람)가 과제를 풀기 위해 스스로 그 정보에 접근할 수 있게 만드느냐의 문제입니다. 잘 설계해 두면 개념을 재사용하고 확장할 수 있게 되어 처리 속도가 빨라집니다. 이런 맥락에서 지식 그래프는, 원래는 서로 떨어져 있고 흩어져 있고 정리되지 않았던 정보를, 질서 있게 연결된 형태로 바꿔 놓은 결과물입니다.

둘째는 **지식 학습(knowledge learning)** 입니다. 이것은 NLP와 대규모 언어 모델(LLM) 같은 여러 프레임워크와 기술을 조합해서, 비정형 문서로부터 통찰을 캐내는 일입니다. 말하자면 지식 표현이 "어떻게 담을 것인가"라면, 지식 학습은 "어떻게 캐낼 것인가"에 해당합니다.

텍스트 데이터로부터 지식 그래프를 만드는 일이 얼마나 까다로운지를 생생하게 보여 주기 위해, 이 장은 실제 프로젝트 하나를 깊이 파고듭니다. 그러면서 비정형 정보를 캐낼 때 부딪히는 문제들을 어떻게 극복하는지 함께 살펴보겠습니다.

## 5.1 아카이브라는 도전 — 역사 기록의 산을 마주하기

**아카이브(archive, 기록보관소)** 는 현재와 과거를 아우르는 아주 넓은 주제와 개념을 담고 있고, 복잡함의 정도도 언어 스타일도 제각각인 데이터 원천을 품고 있습니다. 그 데이터는 대개 비정형입니다. 책, 보고서, 회의록, 연구비 지원 결정서 같은 문서들이 그 예입니다. 이 장과 다음 장에서는 그 방대한 자료 가운데, **록펠러 아카이브 센터(Rockefeller Archive Center, RAC)** 가 소장한 현대 과학 분야의 기원에 관한 역사 데이터의 일부에 초점을 맞춥니다.

RAC는 단순히 과거와 현재의 문서를 쌓아 둔 창고가 아닙니다. 이곳은 미국의 여러 재단, 개인 기부자, 시민사회 단체가 영향을 끼친 **자선(philanthropy)** 과 연구 분야를 연구하는 연구 센터이기도 합니다. RAC는 록펠러 재단(Rockefeller Foundation), 포드 재단(Ford Foundation)을 비롯해 40곳이 넘는 자선 재단, 연구 기관, 문화 단체의 기록을 보유하고 있으며, 이 기록을 전 세계 연구자가 이용할 수 있도록 열어 두고 있습니다.

### 록펠러 재단 — 이 프로젝트의 무대

록펠러 재단은 1913년에 세워진, 미국에서 가장 이른 시기의 대형 자선 기관 가운데 하나입니다. 존 D. 록펠러(John D. Rockefeller), 그의 아들, 그리고 사업 고문이었던 프레더릭 테일러 게이츠(Frederick Taylor Gates)가 함께 세웠습니다. 록펠러는 당대에 미국 역사상 가장 부유한 사람이었습니다. 전성기에는 미국 석유 생산의 90%를 좌지우지했다고 합니다. 그는 자신의 상속자들이 "물려받은 재산을 탕진하거나 권력에 취해 버릴지도" 모른다고 걱정했고 [1], 그래서 게이츠는 "인류의 선을 위한 영구적인 법인 자선 기구"를 만들자는 생각을 북돋웠습니다. 그 목표를 향해 록펠러는 철강왕 앤드루 카네기(Andrew Carnegie)를 포함한 다른 산업가들과 함께, 목표를 정해 놓고 베푸는 현대적 자선의 방식을 정립했고, 자기 이름을 딴 재단들을 세웠습니다.

우리의 목표는, 이런 연구비 지원 결정이 무대 뒤에서 실제로 어떻게 이루어졌는지를 밝혀내는 것입니다. 이를 위해 그림 5.1의 정신 모형(mental model)에 그려진 단계들을 따라, 품질 높은 도메인 특화 지식 추출 시스템을 설계해 보겠습니다.

그림 5.1 도메인 특화 비정형 텍스트 데이터에서 구조화된 지식으로 가는 경로. 각 단계는 문서 디지털화를 위한 광학 문자 인식, 개체명 인식, 관계 추출 시스템 같은 최신 머신러닝 모델에 기댑니다.

록펠러 재단이 어떤 프로젝트에 연구비를 줄지 고르는 과정은 **프로그램 담당관(program officer)** 들에게 크게 의존했습니다. 이들은 연구비를 줄 만한 가치가 있는 연구 영역을 콕 집어내는 사람들이었습니다. 담당관들은 연구자들의 인맥을 쌓고, 그 인맥 바깥에서도 추천을 찾아 다니면서, 자기 전문 분야에 대한 깊은 지식을 길렀습니다. 그들은 회의, 전화 통화, 저녁 식사 자리에서 오간 이야기를 자기 일지(diary)에 적어 두었습니다. 그것도 대개는 타자기로, 급하게, 각종 축약과 약어와 그 분야 특유의 전문 용어를 써 가며 휘갈겨 적었습니다. 이 일지들은 세세한 지식은 물론이고 직업적·개인적 관찰까지 담긴, 그야말로 보물 창고입니다. 이 정보를 제대로 캐내고 모델링하면, 다음과 같은 질문에 답할 수 있습니다.

- 어떤 아이디어에 연구비가 지원되기 전에, 전형적으로 앞서 나타나는 패턴이 있을까요?
- 연구비를 받은 프로젝트들은 영향력 있는 과학자나 이전 수혜자의 추천을 따르는 경향이 있을까요?
- 하나의 연구비가 확정되기 전에, 내부 논의가 몇 번이나 오갈까요?
- 하위 분야별 지원에 어떤 흐름이 있을까요? 그 흐름은 시간이 지나면서 바뀔까요?

이 장은 최신 머신러닝 기술을 특정 도메인에 맞게 어떻게 조정하고, 비정형 데이터에서 복잡한 지식을 어떻게 캐내는지를 보여 줍니다. 이어지는 6장에서는 여기서 뽑아낸 정보로 실제 지식 그래프를 만들고, 그동안 비정형 문서 속에 갇혀 있던 관계 정보에 대한 복잡한 질문에 답해 보겠습니다.

## 5.2 지식 추출의 핵심 개념 — 개체와 관계, 두 개의 기둥

텍스트 데이터를 구조화된 지식 그래프로 바꾸는 일은, 근본적으로 두 가지 작업을 중심으로 돌아갑니다. 하나는 글 속에서 **개체(entity)** 를 찾아내는 것이고, 다른 하나는 그 개체들을 이어 주는 **관계(relationship)** 를 뽑아내는 것입니다. 서로 맞물린 이 두 요소가 어떤 지식 그래프든 그 뼈대를 이룹니다. 이 절에서는 지식 추출의 이 두 가지 구성 요소를 하나씩 살펴봅니다.

### 5.2.1 개체명 인식하기 — 글 속 주인공 찾아내기

텍스트(또는 다른 비정형 데이터 원천)에서 지식 그래프로 가는 첫 단계는 **개체명 인식(named entity recognition, NER)** 입니다. NER은 원본 텍스트 안에서 개체명이 언급된 부분을 찾아내, 미리 정해 둔 범주에 넣어 주도록 학습된 머신러닝 분류 시스템입니다. 쉽게 말해 "이 단어는 사람 이름이야", "이건 기관 이름이야" 하고 표시해 주는 시스템입니다. 개체명을 인식하는 일은 실제 비즈니스에서 쓰임새가 아주 많습니다.

- 여러 데이터 원천의 문서를 서로 연결해 통찰을 발견하기 (예: 금융 문서에 언급된 사람을 기업 등록부의 정보와 연결하기)
- 회사의 정보 관리와 데이터 거버넌스 개선하기
- 데이터 컴플라이언스 시스템의 기반 다지기
- 검색 능력 향상시키기
- 원인과 결과를 이어 주기 (예: 기상 조건과 항공기 지연)

많은 오픈소스 NLP 라이브러리가 사람(Person), 장소(Location), 조직(Organization) 같은 일반적인 개체 범주를 곧바로 쓸 수 있는 모델로 제공합니다. 하지만 이런 일반 범주만으로는 충분한 경우가 드뭅니다. 예를 들어 그림 5.2는 록펠러 재단의 프로그램 담당관이었던 워런 위버(Warren Weaver)의 일지에서 뽑아낸 한 항목을 보여 줍니다.

### 5.2.2 관계 추출하기 — 개체들을 이어 주는 실

텍스트 데이터에서 지식 그래프로 가는 두 번째 단계는 **관계 추출(relation extraction, RE)** 입니다. 이것은 텍스트 문서 안에서 개체 쌍 사이의 의미적 관계를 찾아내는 일입니다. 예를 들어 다음 문장을 봅시다. "제인 오스틴(Jane Austen), 빅토리아 시대 작가는 현재 구글에 고용되어 있다." 이 문장에는 PERSON(사람) 부류의 개체 "제인 오스틴"과 ORGANIZATION(조직) 부류의 개체 "구글"이 언급되어 있고, 이 두 개체는 서로 긴밀하게 이어져 있습니다. 하나가 다른 하나의 피고용인이라는 관계입니다. 바로 이 "이어져 있음"을 붙잡아 내는 것이 진정한 지식 그래프를 만드는 핵심입니다. 개체만 따로 뽑아 놓으면 흩어진 점들일 뿐이고, 그 점들을 잇는 선(관계)이 있어야 비로소 그래프가 됩니다.

> **참고** 이런 관계를 모델링하는 방법은 여러 가지입니다. 예를 들어 "제인 오스틴 – WORKS\_FOR -> 구글"처럼 나타낼 수도 있고, "제인 오스틴 <– EMPLOYS - 구글"처럼 EMPLOYS(고용한다) 관계로 방향을 뒤집어 나타낼 수도 있습니다. 중요한 것은 여러 문서에 걸쳐 **일관성** 을 지키는 것입니다. 같은 개념을 어떤 문서에서는 WORKS_FOR로, 다른 문서에서는 EMPLOYS로 제각각 표현하면 나중에 그래프가 뒤죽박죽이 됩니다.

## 5.3 대규모 언어 모델로 지식 그래프 만들기 — 판을 바꾸는 도구

여기까지는 이른바 "전통적인" NLP를 이야기했습니다. 과제에 맞는 학습 데이터셋을 만들고, 가장 좋은 모델 구조를 찾고, 하이퍼파라미터를 미세 조정하는 식의 접근입니다. 이 과정의 상당 부분은 학습 데이터의 품질을 끌어올리는 일에 쓰입니다. 그런데 이 일은, 좋게 말해도, 고되기 짝이 없습니다.

2022년 말, OpenAI는 GPT-3.5 계열의 첫 모델들을 공개했습니다. 그 안에는 놀라운 능력을 지닌 챗봇 **ChatGPT** 도 있었습니다. 자연어로 던진 질문이나 과제 설명만 있으면, ChatGPT는 편지 초안을 잡아 주고, 기사를 요약하고, 사실 관계를 묻는 질문에 답하고, 요리법을 번역하고, 지정한 이미지를 만들어 내고, 파이썬 코드를 작성하는 등 훨씬 더 많은 일을 해냅니다. 이런 종류의 **생성 모델(generative model)** 을 **대규모 언어 모델(large language model, LLM)** 이라 부르며, 이것은 **트랜스포머(Transformer) 구조** [2] 위에 세워져 있습니다.

LLM의 핵심 개념은 **전이 학습(transfer learning)** 입니다. 전이 학습이란, 어떤 일반적인 과제(예: 무작위로 가려진 토큰을 맞히기)에서 배운 언어 패턴과 지식을, 다른 과제(예: 관계 추출)에 그대로 재사용하는 능력입니다. 이 덕분에 지도 학습(supervised learning)에 필요한 학습 데이터셋의 크기가 크게 줄어듭니다. 모델을 처음부터 다시 학습시키는 게 아니라, 방대한 데이터셋에서 이미 배워 둔 가중치(weight)를 다시 쓰기 때문에, 사람이 직접 라벨을 단 데이터가 적어도 같은 정확도에 이를 수 있습니다.

LLM을 예외적으로 뛰어나게 만드는 것은 두 가지입니다. 하나는 모델의 복잡도(파라미터 개수)이고, 다른 하나는 학습에 쓴 말뭉치(corpus)의 크기와 품질입니다. 신경망이 더 클수록(즉 학습 가능한 파라미터가 더 많을수록), 테스트셋 손실(test-set loss) 기준으로 같은 성능에 이르는 데 필요한 데이터 표본이 더 적어집니다 [3]. 놀랄 일도 아니지만, 모델이 배울 데이터가 많을수록 모델은 더 좋아집니다. 하지만 이것은 데이터의 양만의 문제가 아니라 데이터의 품질에 관한 문제이기도 합니다. 전통적인 머신러닝에서는 초점이 주로 가장 좋은 모델 구조를 찾고 하이퍼파라미터를 미세 조정하는 데 쏠려 있었습니다. 이런 **모델 중심(model-centric) 접근** 은, 극단으로 가면 데이터 품질 문제를 무시해 버립니다. 그리고 엉터리 데이터를 넣으면 엉터리 예측이 나온다는 것은 전혀 놀랄 일이 아닙니다. 시간이 흐르면서 **데이터 중심(data-centric) 패러다임** [3]이 힘을 얻었는데, 이것은 복잡도가 높은 머신러닝 모델을 학습시키는 데 쓰는 데이터의 품질(과 양)을 끌어올리는 데이터 엔지니어링에 초점을 둡니다. 그 결과, 오늘날의 LLM은 너무나 강력해져서 우리는 그저 자연어로 과제를 표현하기만 하면(이것이 **프롬프트 엔지니어링** 입니다) 모델이 답을 만들어 냅니다. 더 이상 모델 엔지니어링이 필요하지 않습니다.

LLM 일반, 특히 OpenAI의 GPT 계열 모델이 어마어마한 능력을 지녔지만, 이런 모델에 의존하는 시스템을 설계할 때는 몇 가지 한계를 반드시 염두에 두어야 합니다. 우리 사례에서 가장 중요한 한계는 **환각(hallucination)** 입니다. 환각이란, 학습 데이터에 그 답을 뒷받침할 근거가 전혀 없는 상황에서도 모델이 "사실"을 지어내고 잘못된 추론을 하는 경향을 말합니다. 예를 들어 우리가 ChatGPT에게 NASA의 SLS 로켓 비용을 물었는데 학습 데이터에 그런 정보가 없다면, 모델은 아무 숫자나 골라 놓고 그게 비용이라고 주장할 수 있습니다. 바로 여기서 앞서 말한 "달변가 LLM"의 위험한 얼굴이 드러납니다. 모를 때조차 자신 있게 말을 지어내는 것이죠. OpenAI 팀이 이 행동을 억제하려 애쓰고 있지만, 이 글을 쓰는 시점까지도 이것은 여전히 풀리지 않은 문제로 남아 있습니다.

이런 성취에도 불구하고, 우리는 이 모델들을 "AI"라고 부르지는 않겠습니다. 진정한 인공지능에 이르기까지는 아직 갈 길이 멉니다. 그보다 우리는 LLM을 이용해 더 포괄적이고 더 깨끗한 지식 그래프를 만들자고 제안합니다. LLM에게 품질 높은 개체명, 관계, 속성을 뽑아 달라고 요청하는 식으로 말입니다. 그림 5.3의 정신 모형이 이 그림을 다시 상기시켜 줍니다.

### 5.3.1 LLM 활용하기 — 그냥 쓸까, 길들여 쓸까

LLM으로 지식 그래프를 만드는 데는 두 가지 길이 있습니다. 하나는 **프롬프트 기반 추론(prompt-based inference)** 으로 별다른 손질 없이 바로 쓰는 것이고, 다른 하나는 **파인튜닝(fine-tuning)** 을 통해 우리 도메인에 특화된, 더 정확하고 안정적인 출력을 내도록 길들이는 것입니다. LLM은 우리가 그저 과제를 자연어로 표현하고 (선택적으로) 예시 하나만 붙여 줘도, 손질 없이 곧바로 꽤 잘 해내는 경우가 많습니다. 이렇게 과제를 표현한 것을 **프롬프트(prompt)** 라 하고, 주어진 과제에 가장 성능이 좋은 프롬프트를 찾아가는 반복 과정을 **프롬프트 엔지니어링(prompt engineering)** 이라 부릅니다.

이 장에서 우리가 관심을 두는 것은 **텍스트 완성(text completion)** 입니다. 모델에게 프롬프트를 주면, 모델은 그 프롬프트 안의 맥락과 과제 설명에 맞춰 텍스트를 생성합니다. 우리의 목표는 GPT의 힘을 이용해, 텍스트 입력으로부터 개체와 그 개체들 사이의 관계를 찾아내는 것입니다. 이 과정은 그림 5.4에 도식으로 정리되어 있습니다.

![텍스트 데이터로부터 지식 그래프를 만들 때 LLM이 하는 두 가지 역할. 위쪽 갈래는 프롬프트 기반 접근, 아래쪽 갈래는 파인튜닝 접근입니다.](images/ko/figure-5-4-ko.png)

그림 5.4 텍스트 데이터로 지식 그래프를 생성할 때 LLM의 두 가지 역할: 프롬프트 기반 접근(위쪽 갈래)과 파인튜닝 접근(아래쪽 갈래)

데이터 과학 프로젝트가 늘 그렇듯, 우리도 **데이터 탐색(data exploration)** 부터 시작합니다. 우리가 다루는 도메인, 앞에 놓인 난관, 결과에 대한 합리적인 기대치를 이해할 필요가 있기 때문입니다. 예를 들어, 이 장 앞부분에 나온 일지 항목을 떠올려 보세요. 인터뷰 대상이었던 C. G. 로스비(C. G. Rossby)는 항목 첫머리에서만 성과 이름을 다 써서 소개되고, 그 뒤로는 그냥 "R."로만 지칭됩니다. 그러니 우리는 사람을 이렇게 흔치 않은 방식으로 가리키는 문제를 풀어낼 수 있도록 지식 추출 시스템을 설계해야 합니다.

그다음 단계는 프롬프트 엔지니어링입니다. 대개 가장 쓸 만한 프롬프트를 찾아내기까지 여러 번의 반복이 필요합니다. 단어 몇 개만 바꿔도 때로는 성능에 큰 차이가 나기 때문입니다. 우리는 과제를 최대한 정확하게 기술해서 모호함을 줄여야 합니다. 모호하게 놔두면 모델이 답을 지나치게 창의적으로 지어낼 여지를 주게 되니까요.

프롬프트 엔지니어링을 마치면 두 갈래 중 하나에 이릅니다. 답의 품질에 만족해서 곧바로 지식 그래프 생성으로 넘어가거나, 아니면 이 과제가 프롬프트 기반 접근만으로 감당하기엔 너무 복잡하다는 걸 깨닫거나 입니다. 후자의 경우, 우리는 작은 학습 데이터셋을 준비합니다. 이 데이터셋은 프롬프트(과제 설명 없이 순수한 입력 문서만)와 기대 출력의 쌍으로 이루어집니다. (앞서 한 프롬프트 엔지니어링 작업은 헛수고가 아닙니다. 사람이 최종 주석을 달기 전에, 이 프롬프트로 데이터셋을 미리 초벌 주석(preannotate)해 둘 수 있기 때문입니다.) 데이터셋이 준비되면 OpenAI의 API를 이용해 모델을 파인튜닝할 수 있습니다. 첫 번째 반복만으로 만족스러우면 그것으로 지식 그래프를 만들면 되고, 아직 충분치 않으면 학습 데이터를 더 넣고 다시 시도하며 과정을 반복합니다. 이 과정에는 시간과 돈이 들지만, 그 대가로 우리 도메인에 특화되어 더 안정적이고 정확한 출력을 내주는 모델을 얻게 됩니다.

### 5.3.2 프롬프트 엔지니어링 예시 — 프롬프트를 진화시켜 가기

프롬프트 엔지니어링을 좀 더 가까이 들여다봅시다. 다음 프롬프트는 GPT에게 모든 개체와 그 개체들 사이의 관계를 찾아 달라고 요청합니다.

**리스팅 5.1** 프롬프트 버전 1: 개체와 관계 찾아내기

```python
def openai_query(client, prompt_segments: dict, query: str):
    # 상태를 저장하지 않는(stateless) ChatGPT API 질의를 실행하는 함수
    messages = [
        {"role": "system", "content": prompt_segments['task']},
        {"role": "user", "content": prompt_segments['example']},
        {"role": "assistant", "content": prompt_segments['example_output']},
        {"role": "user", "content": query}
    ]
    t_start = time.time()
    # 모델, 온도(temperature) 등의 파라미터를 지정
    response = client.chat.completions.create(model=OPENAI_MODEL,
        messages=messages, temperature=0., max_tokens=2000)
    print(response.choices[0].message.content)
    print(f"\nTime: {round(time.time() - t_start, 1)} sec\n")
    return response.choices[0].message.content

if __name__ == "__main__":
    client = OpenAI(api_key=os.environ['OPENAI_API_KEY'])
    # 처리할 텍스트
    text = """
JOHNS HOPKINS UNIVERSITY Chemistry Department:
Wednesday, November 9, 1932
WW visits the Dept. with Dr. Frazer (Baker Prof. Chem.). There are 239

cluding holders of the special State fellowships in chemistry under the
New Plan. D.H. Andrews (Prof.Chem.) is a physical chemist specializing in

of the mathematician, is working on an experimental problem. Andrews says
that Mayer is young and impresses one as an enthusiastic and able man.
"""
    openai_query(client, prompt_segments, text)
```

이 코드에서 눈여겨볼 대목이 몇 가지 있습니다. 메시지를 구성할 때 과제 설명은 `system` 역할로, 예시 입력은 `user` 역할로, 예시 출력은 `assistant` 역할로 넣습니다. 즉 "이런 질문에는 이렇게 답하는 거야" 하고 모델에게 한 차례 시범을 보여 준 뒤, 진짜 처리할 텍스트를 마지막 `user` 메시지로 던지는 구조입니다. 또한 `temperature=0.`으로 온도를 0으로 맞췄는데, 이는 뒤에서 자세히 설명하겠지만 사실을 뽑아내는 과제에서 출력을 최대한 결정적으로 만들기 위한 설정입니다.

결과는 고무적입니다. 예를 들어 D. H. 앤드루스와 J. B. 마이어에 관해 뽑아낸 관계들은 다음과 같습니다.

```text

["D.H. Andrews", "person", "specializes in", "thermodynamics", "field"]
["D.H. Andrews", "person", "is measuring", "specific heats of organic
compounds", "research"]
["D.H. Andrews", "person", "is interested in", "mechanical models of

["J.B. Mayer", "person", "is a former student of", "G. N. Lewis", "person"]

["J.B. Mayer", "person", "works at", "Gottingen", "location"]
["J.B. Mayer", "person", "specializes in", "energetics of crystal

```

인상적입니다! D. H. 앤드루스는 실제로 화학과 교수이고, 앞에서 뽑아낸 모든 연구 주제에 관여하고 있습니다. 마찬가지로 J. B. 마이어에 대해서도 그의 직함, 전문 분야, 누구 밑에서 배웠는지를 알아냈습니다. 게다가 이 관계들에는 성과 이름이 온전히 담겨 있습니다. 원본 일지 항목에서는 그냥 "Mayer" 또는 "he(그)"라고만 언급했는데도 말입니다.

이 대목이 특히 놀라운 이유가 있습니다. 전통적인 관계 추출이었다면, NER 모델이 먼저 개체 언급("Mayer")을 찾아내고, 그다음 **상호참조 해소(coreference resolution)** 모델을 써서 "Mayer"와 "he"를 온전한 이름으로 이어 준 뒤, 마지막으로 관계 추출을 돌려서 관계와 해소된 이름을 얻어야 했을 것입니다. 여기서는 LLM의 생성적 특성 덕분에 상호참조 해소가 암묵적으로 처리됩니다. 모델이 문서 전체 맥락에 대한 자기 이해를 바탕으로 출력을 생성하기 때문입니다. 마지막으로, 직함이 "Prof. Chem."과 "Assoc. in Chem."에서 "Professor of Chemistry(화학과 교수)"와 "Associate in Chemistry(화학과 조교)"로 풀려 나온 것도 눈여겨보세요. 모델이 줄임말에서 올바른 전체 직함을 추론해 낸 것입니다. 어떤 전통적인 NER 모델도 이런 일은 하지 못합니다.

이제 개체 사이의 관계 유형을 살펴봅시다. 극단적인 세밀함(자세함의 정도)에 주목하세요. "specializes in(~을 전문으로 한다)", "is measuring(~을 측정하고 있다)", "is interested in(~에 관심이 있다)", "demonstrates(~을 입증한다)"는 모두 정확한 표현입니다. 하지만 이 출력이 지식 그래프에 쓸모가 있을까요? 이것들은 모두 같은 개념을 나타냅니다. 사람이라면 아마 이 넷에 "works on(~에 관해 일한다)" 같은 하나의 관계 유형을 붙일 텐데, GPT는 우리에게 네 가지 서로 다른 유형을 준 것입니다! 게다가 이건 겨우 짧은 한 문단에서 나온 결과입니다. 만약 수천 쪽을 처리한 다음 "누가 유기 화합물 연구를 하는가?" 같은 질문에 답하려 든다면, 지식 그래프 스키마가 어떤 꼴이 될지 상상해 보세요. "works on"이라는 상위 개념에 해당하지 않는 결과를 걸러 내려면, 우리는 의미가 같거나 매우 비슷한 관계 유형을 전부 알아내서 Cypher 질의에 일일이 나열해야 할 것입니다. 좋게 말해도 실용적이지 않은 일입니다.

노드 라벨(node label)도 마찬가지입니다. 이 문단의 연구 주제 네 개에는 서로 다른 세 개의 라벨이 붙었습니다. field(분야), research(연구), theory(이론)입니다. 본질적으로는 다 맞는 말입니다. 하지만 이것들이 진짜로 무엇일까요? 이것들은 모두 앤드루스 교수의 연구 주제입니다. 그러니 사람이라면 이 각각을 topic(주제)이나 occupation(직무)이라고 부르고, 그래프에서는 이 전부에 대응하는 단 하나의 노드 라벨을 가질 것입니다.

마지막으로, 이 출력에서 마이어의 성격에 관한 언급이 빠진 것을 알아채셨나요? 아니면 모델이 "straight calorimetric method(직접 열량 측정법)"에 대한 언급을 무시하고, "theory of Raman spectra(라만 스펙트럼 이론)"와 얽힌 관계를 놓친 것은요? 그래서 우리는 다시 한번 시도해 보기로 했습니다. 같은 프롬프트, 같은 모델 설정으로 같은 텍스트에서 개체와 관계를 생성해서, **예측 안정성(prediction stability)** 을 시험한 것입니다. 즉 LLM이 두 번째에도 같은 출력을 내는지 본 것입니다. 답은 "아니오"였습니다. 예를 들어 두 번째 실행에서는, 첫 번째에서 제대로 찾아냈던 라만 스펙트럼 이론이 빠졌고, 직접 열량 측정법도 함께 빠졌습니다. 모델은 앤드루스가 마이어의 성격에 대해 이야기했다는 것은 인정했지만(우리는 `["D.H. Andrews", "person", "describes", "J.B. Mayer", "person"]`이라는 관계를 얻었습니다) 그가 마이어에 대해 뭐라고 말했는지는 붙잡아 내지 못했습니다. 이 결과는, 다운스트림 분석과 과제에 쓸 지식 그래프를 만들려고 문서에서 지식을 캐낼 때, "모든 개체와 그 사이의 관계를 찾아내라" 식의 두루뭉술한 프롬프트에만 기대면 예측이 불안정해지는 문제를 잘 보여 줍니다.

그래서 리스팅 5.4에 나오는 새로운 버전의 프롬프트를 시험해 봅시다. **정규화(normalization) 문제** 를 다루기 위해, 개체 부류와 관계 유형의 목록을 넣고, 성능이 떨어지는 몇몇 관계 유형에 대해서는 설명까지 곁들였습니다.

> **팁** 이렇게 단순한 목록을 쓰는 대신, 여기에 완전하고 권위 있는 지식 그래프 스키마 전체를 명시할 수도 있습니다. 하지만 그렇게 하면, 우리가 미처 생각하지 못한 개체와 관계가 포함된 출력이 나올 여지를 닫아 버리게 됩니다.

또한 우리는 과제 설명에 두 가지 참고 사항을 덧붙여, 모델을 이끌고 예측 안정성을 높였습니다. 하나는 사람을 이니셜로 지칭하는 습관을 설명한 것이고, 다른 하나는 대학과 학과 이름의 별칭(aliasing) 사용을 언급한 것입니다.

### 5.3.3 프롬프트 엔지니어링 지침 — 오래도록 통하는 원칙들

LLM은 빠르게 진화하고 있어서, 금세 낡아 버릴 기술적 지침을 공유하는 것은 별 의미가 없습니다. 하지만 몇몇 일반적인 배움의 지점은 더 새로운 모델에도 그대로 옮겨 갈 수 있습니다. RAC 프로젝트를 진행하며 우리가 발견한 핵심 원칙들을, 다음의 프롬프트 엔지니어링 모범 사례로 정리해 두었습니다.

#### 과제 설명과 도메인 특화 지침 (TASK DESCRIPTION AND DOMAIN-SPECIFIC GUIDANCE)

잘 설명된 과제는 출력의 품질과 안정성에 아주 중요합니다. 여러 가지 표현을 실험해 보고, 지금 다루는 데이터셋의 특성을 덧붙일 가치가 있습니다. 우리 예시에서는 사람을 축약과 이니셜로 지칭하는 습관을 명시한 것이 그런 특성이었습니다.

#### 개체와 관계 부류의 이름 짓기 (NAMING OF ENTITY AND RELATION CLASSES)

프롬프트에는 여러분이 가장 관심 있는 개체와 관계 부류의 목록을 넣으세요. 이것은 과제를 분명하게 하고 더 정규화된 출력을 얻는 데 도움이 됩니다. 그리고 어떤 용어를 고르느냐가 정말 중요합니다! 만약 어떤 개체나 관계 부류의 성능이 떨어진다면, 이름을 바꿔 보세요. 예를 들어 우리는 처음에 일지 항목 속 대화의 주제를 Topic(주제)이라고 불렀는데, 이 용어가 개체 부류로 쓰기엔 너무 두루뭉술하다는 것을 깨달았습니다. 이것을 Occupation(직무)으로 바꾸자, 다른 부분은 똑같은 프롬프트가 훨씬 더 포괄적이고 안정적인 결과를 냈습니다.

#### 복잡하고 대표적인 예시 (COMPLEX AND REPRESENTATIVE EXAMPLES)

개체·관계 추출처럼 복잡한 과제에서는, 입력과 기대 출력의 예시를 프롬프트의 일부로 제공하는 것이 유용합니다. 그 예시는 실제로 처리해야 하는 텍스트를 압축한 버전이어도 되며, 중요한 개체와 관계의 사례를 담고 있으면 됩니다. 데이터셋에 등장하는 복잡한 언어 표현을 포함시키고, 모델이 특히 어려워하는 관계에 초점을 맞추세요. 또한 예시는 최대한 대표성을 갖게 만드세요. 예시가 여러분의 핵심 관계 유형을 모두 담고 있는지 꼭 확인해야 합니다.

#### LLM 설정 (LLM CONFIGURATION)

여러 LLM을 실험해 보고 여러분에게 가장 잘 맞는 것을 고르세요. 그리고 파라미터, 특히 **온도(temperature)** 를 시험해 보세요. 온도가 높을수록 출력이 더 다채롭고 창의적으로 나옵니다(그리고 환각을 일으킬 성향도 더 커집니다). 온도가 낮을수록 더 결정적인 출력이 나옵니다. 그래서 텍스트 생성 같은 창의적 과제는 더 높은 온도로 하는 편이 낫고, 코드 생성 같은 과제는 더 낮은 온도(0.2 안팎)를 필요로 합니다. 문서에서 개체와 관계를 뽑아내는 것처럼 사실에 초점을 둔 과제라면, 우리는 온도를 0으로 씁니다.

#### 예측 안정성 시험하기 (TESTING PREDICTION STABILITY)

LLM은 생성 모델이라는 점을 기억하세요. 그래서 정의상, 그들은 "기분(mood)"을 가질 수 있고 실제로 가집니다. 같은 프롬프트라도 같은 텍스트에 여러 번 돌리면 다른 결과가 나올 수 있습니다. 여러분은 이 행동을 신중한 프롬프트 엔지니어링(모호하지 않은 과제 설명)과 아주 낮은 온도 설정(방금 이야기한 대로)으로 억제할 수 있습니다. 만약 0이 아닌 온도를 골랐다면, 같은 프롬프트를 같은 테스트 데이터셋에 여러 번 돌려 보고 결과가 얼마나 겹치는지 평가함으로써 예측 안정성을 시험해 보세요. 사실적 지식을 캐낼 때 절대로 원치 않는 것 하나가 있다면, 그것은 바로 불안정한 예측 행동과, 결과로 나온 지식 그래프에 대한 낮은 신뢰입니다!

#### 프롬프트 단위 테스트하기 (UNIT-TESTING THE PROMPT)

프롬프트 엔지니어링은 빠르고 간단한 작업이어야 하지만, 때로는 원하는 결과를 얻기까지 아주 많은 반복이 걸릴 수 있습니다. 그러니 코드 개발에서와 마찬가지로, 간단한 단위 테스트 시스템을 세우는 것을 고려해 보세요. 프롬프트를 업데이트할 때마다 텍스트 토막과 기대 출력을 테스트 목록에 추가하고, 몇 번 반복할 때마다 이 테스트 목록을 한꺼번에 돌려서 성공률을 계산하고 실패 사례를 출력해 살펴보는 식입니다. 이렇게 하면 이전 반복에서 이룬 성과를 하나도 잃어버리지 않게 됩니다.

#### 미니 지식 그래프 눈으로 확인하기 (EYEBALLING A MINI-KG)

프롬프트가 하나의 이정표(milestone)에 이를 때마다, 문서의 작은 표본(몇십 쪽 정도)에 프롬프트를 적용해서 지식 그래프를 만들어 보길 권합니다. 왜냐고요? 우리 인간은 감각의 존재라서, 짐작하고 상상하는 것보다 직접 보고 만지는 것이 때로는 훨씬 더 도움이 되기 때문입니다. 작게 만든 지식 그래프를 잠깐 들여다보는 것만으로도 개선의 실마리를 발견하는 경우가 많습니다.

> **정의** 프롬프트 엔지니어링은 반복적인 과정입니다. 원래의 과제를 해결하는 데 상당한 진전을 이뤘다고 느껴질 만큼 프롬프트 개선을 충분히 모았을 때, 여러분은 하나의 **프롬프트 이정표(prompt milestone)** 에 이른 것입니다.

예를 들어 RAC 그래프를 둘러보다가, 우리는 U. of PA처럼 축약된 형태의 조직 이름이 많다는 것을 발견했습니다. GPT는 학습 중에 얻은 방대한 일반 지식 덕분에, 제대로 지시만 해 주면 이것을 University of Pennsylvania(펜실베이니아 대학교)로 채워 넣을 수 있어야 합니다. 마찬가지로 우리는 사람 이름이 S. 같은 형태로 축약된 것도 봤습니다. 또 여러 사람이 같은 조직에서 일하는 것처럼 보였는데, 알고 보니 그저 Department of Physics(물리학과)였습니다. 그런데 어느 대학의 물리학과일까요? 다음 반복에서는 이런 실패를 고려해서, GPT가 우리가 원하는 출력을 내도록 프롬프트 예시에 복잡함을 더했습니다.

#### 평가 (EVALUATION)

프롬프트에 만족하게 되면, **정량적 평가(quantitative evaluation)** 를 하세요. 텍스트 몇십 쪽을 처리하고, 누군가를 품질 보증(QA) 관리자로 지명해서, 예측 결과를 하나하나 훑으며 개체와 관계를 맞음·틀림·누락으로 표시하게 하세요. 그런 다음 개체와 관계에 대해 부류별 **정밀도(precision), 재현율(recall), F1 점수** 를 계산합니다. 참고로 정밀도는 "찾아낸 것 중 맞은 비율", 재현율은 "찾아냈어야 할 것 중 실제로 찾아낸 비율", F1 점수는 이 둘을 하나로 종합한 지표입니다.

QA 관리자는, 몇 개 안 되는 예시로 시험할 때는 발견할 수 없었던 체계적인 실패(systemic failure)를 잡아내기에 좋은 위치에 있습니다. 또 다른 선택지는 **LLM을 심판(judge)으로 쓰는 것** 입니다. 사람에게 묻는 대신, 이 일을 또 다른 강력한 LLM에게 맡기는 것이죠. 물론 그 LLM도 실수를 하겠지만, 사람의 성능이라고 100%인 것도 아닙니다. 어느 쪽을 택하든, 제대로 된 평가는 큰 데이터셋으로 지식 그래프를 만드는 데 시간과 돈을 쏟기 전에 예측 품질에 대한 확신을 줄 것이고, 앞으로의 모델 드리프트(model drift)를 감시하는 기준이 되어 줄 것이며, 프롬프트를 개선할 기회를 한 번 더 줄 것입니다.

#### 초기 탐색용 지식 그래프 (INITIAL EXPLORATIVE KG)

프롬프트 엔지니어링을 하려면 데이터와 그 내용, 그리고 거기서 뽑아내고 싶은 지식에 대해 최소한의 이해가 있어야 합니다. 그런데 우리는 기업들이 자기 콘텐츠의 내용에 대해 어렴풋한 감만 가진 사례를 많이 봤습니다. 뭔가 쓸모 있는 게 들어 있다는 건 알지만, 정확히 무엇을 캐내야 하는지, 즉 지식 그래프 스키마가 어떤 모습이어야 하는지는 모르는 경우입니다. 이럴 때는 데이터 속으로 뛰어들어, 탐색하고 이해하는 데 얼마간 시간을 써야 합니다. 이 잠재적으로 길고 지루한 작업은, 빠르고 일반적인 개체·관계 추출 프롬프트를 설계하고(LLM에게 모든 개체와 관계를 뽑아 달라고 하면서, 출력 형식을 보여 줄 짧은 예시를 주는 식으로), 문서 표본으로 지식 그래프를 만든 다음, 그것을 탐색하고 돌아다니며 영감을 얻는 방식으로 훨씬 수월해질 수 있습니다. 그래요, 그 그래프는 매우 정규화되지 않은 상태일 것입니다. 하지만 그것은 데이터셋의 내용을 빠르게 이해하고, 거기서 어떤 종류의 개체와 관계를 캐낼 수 있는지 파악하고, 프롬프트 엔지니어링을 시작하는 데 도움이 됩니다.

#### 야심 차게 하라 (BE AMBITIOUS)

크게 생각하세요! 어떤 일이 LLM에게 너무 어려울 거라고 넘겨짚지 말고, 그냥 시도해 보세요. LLM은 방대한 데이터로 학습되었고, 깊은 언어 이해와 일반 지식을 갖췄다는 점을 기억하세요. 이들은 이름의 오타 같은 것도 처리할 수 있고, 맥락으로부터 "Prof. Chem."이 Professor of Chemistry라는 직함임을 추론할 수 있으며, "Stanford"라는 언급이 장소나 사람 이름이 아니라 Stanford University(스탠퍼드 대학교)를 뜻한다는 것도 알아냅니다. 그러니 프롬프트에 예시를 줄 때는 야심 차게 하세요. 완전하고 깨끗한 개체 이름으로 관계를 제공하면, 처음부터 더 깨끗하고 정확한 지식 그래프를 얻게 되고, 후처리 과정에서 개체를 정제하고 해소해야 할 필요가 줄어듭니다.

#### 지나치게 생각하지 마라 (DON'T OVERTHINK)

프롬프트 엔지니어링은 **제로샷 학습(zero-shot learning, 과제 설명만 주는 것)** 이나 **원샷 학습(one-shot learning, 예시 하나를 주는 것)** 이라 불리는 단순한 기법입니다. 우리는 방대한 데이터로 사전학습된 모델이, 과제 설명과 예시 한두 개만으로 특정 도메인과 과제에서 잘 해내기를 기대합니다. LLM이 강력하긴 해도, 복잡한 추론 과제를 다룰 때는 이것이 어렵습니다. 언제나 불완전함이 남을 수밖에 없는데, 원샷 학습만으로는 전체 데이터셋에 있는 온갖 복잡함과 모호함을 모델에게 다 대비시킬 수 없기 때문입니다.

그래서 우리의 마지막 조언은 이것입니다. 프롬프트 개발을 과도하게 설계하고 지나치게 고민하지 마세요. 빠른 반복을 몇 번 하고, 이정표마다 미니 지식 그래프를 만들어 눈으로 확인하며 있을 법한 체계적 실패와 개선 후보를 찾아낸 뒤, 다음으로 넘어가세요. 온 힘을 다했는데도 프롬프트 엔지니어링이 만족스러운 결과를 내지 못하는 지점에 이르렀다면, 끝없는 프롬프트 개선에 매달리기보다 남은 프로젝트 시간을 LLM 파인튜닝에 투자하는 편이 낫습니다.

### 5.3.4 지식 그래프 구축: 전통적 NLP인가, LLM인가?

이쯤 되면 여러분은 전통적인 NLP 경로를 따라야 할지, LLM 경로를 따라야 할지 어떻게 정하느냐가 궁금해질 것입니다. AI가 주름잡는 현대 세계에서 전통적 NLP가 설 자리가 있기는 할까요? 각 접근의 장단점부터 살펴봅시다.

**전통적 NLP의 장점** 은 다음과 같습니다.

- **예측 속도** — 더 작고 단순한 모델은 예측을 더 빨리 생성하며, CPU에서도 잘 돌아갑니다.
- **인프라의 단순함과 비용** — 모델을 학습하고 배포하는 데 단순하고 값싼 인프라로 충분하며, GPU가 필요 없는 경우도 많습니다.
- **예측 비용** — 인프라가 단순하고 저렴한 덕분에 예측 비용이 아주 낮습니다.
- **보안** — 격리된 안전한 배포를 위한 온프레미스(on-premises) 솔루션을 구성하기가 더 쉽고 저렴합니다.

**전통적 NLP의 단점** 은 다음과 같습니다.

- **사내 전문성** — 설계, 학습, 배포, 유지보수에 고도로 전문화된 데이터 과학 전문성이 필요합니다.
- **복잡한 NLP 파이프라인 구성** — NER, 관계 추출, 상호참조 해소, 개체 해소, 중의성 해소처럼 전문화되고 맞춤화된 모델들이 필요합니다.
- **데이터 주석의 복잡함과 비용** — 각 모델을 여러분의 도메인에 맞게 여러분의 데이터로 학습시켜야 하고, 이를 위해 품질 높은 학습 데이터셋을 여러 개 만들어야 합니다. 이 과정에는 시간, 데이터 과학 전문성, 인프라, 소프트웨어가 듭니다. 초기 투자가 아주 크고, 특히 관계 추출처럼 복잡한 과제에서는 결과가 보장되지도 않습니다.

**LLM의 장점** 은 다음과 같습니다.

- **초기 도메인 맞춤화 비용** — 전이 학습과 프롬프트 엔지니어링 덕분에, 여러분의 특정 도메인에서 실제 서비스에 이르는 길이 훨씬 빠릅니다.
- **완만한 학습 곡선** — 전문 데이터 과학자 없이도 빠르게 시작하고 노하우를 쌓을 수 있습니다. 최소한의 기술적 소양만 있으면 누구나 프롬프트 엔지니어링과 파인튜닝을 배울 수 있습니다.
- **올인원 NLP** — 목표에 이르기 위해 여러 개의 (그러나 서로 의존하는) 처리 단계를 따로따로 설계할 필요가 없습니다. 데이터를 한 번 통과시키는 것으로 모든 게 해결됩니다.
- **생성적 특성** — 처리 파이프라인이 단순할 뿐 아니라, 전이 학습과 LLM의 생성적 특성 덕분에 결과의 품질도 높습니다. 이들의 맥락적·언어적 이해와 추론은, 어떤 전통적 NLP 모델보다도 더 깨끗하고 정확한 지식 그래프를 처음부터 만들어 냅니다.
- **더 단순한 후처리** — LLM의 생성적 특성과 언어 이해 덕분에, 후처리(정제, 정규화, 개체 해소)가 덜 필요합니다.

**LLM의 단점** 도 있습니다.

- **예측 속도** — 거대한 모델은, 강력한 GPU 위에서 서비스되더라도, 예측 속도가 훨씬 느립니다.
- **인프라의 복잡함** — GPU가 학습뿐 아니라 예측에도 반드시 있어야 하기 때문에, 인프라의 복잡함과 비용이 더 높습니다.
- **파인튜닝 비용** — 프롬프트 엔지니어링만으로 부족하면 모델을 파인튜닝해야 합니다. 이는 학습 데이터셋 준비, 인프라, 예측에 드는 비용이 더 높아진다는 뜻입니다. (OpenAI는 맞춤 모델로 예측을 돌릴 때 10배를 더 청구하며, 온프레미스 배포라 해도 모델 버전을 유지·관리하는 비용을 고려해야 합니다.)
- **아주 큰 데이터셋에서의 예측 비용** — 중소 규모 데이터셋이라면, LLM을 쓰는 것이 맞춤형 전통 NLP 파이프라인을 만드는 초기 투자보다 아마 더 쌀 것입니다. 하지만 방대한 데이터셋을 가졌다면 셈이 꽤 달라질 수 있습니다.
- **보안/온프레미스 배포 비용** — 보안이 중요한 도메인에서 일한다면, 특히 클라우드 제공자를 쓸 수 없어 직접 GPU 클러스터를 세우고 배포하고 유지해야 한다면, 행운을 빕니다.

> **참고** 요즘에는 폐쇄형 소스든 오픈소스든 많은 LLM이 아마존 웹 서비스(AWS), 애저(Azure), 구글 클라우드 플랫폼(GCP) 같은 하이퍼스케일러를 통해 제공됩니다. 이 덕분에 방금 언급한 고충 가운데 일부는 덜어집니다.

그렇다면 처음의 질문, "AI가 주름잡는 현대 세계에서 전통적 NLP가 설 자리가 있는가?"에 답해 봅시다. 우리의 답은 "당연히 있다!"입니다. LLM과 지식 그래프의 결합에 밝은 미래가 있으리라 내다보면서도, 우리는 다른 기술(NLP 같은)이 설 자리가 여전히 상당히 넓다고 봅니다. 특히 보안 요구, 비용(방대한 데이터셋), 그리고 스트리밍 시나리오(예측 속도)를 고려하면 그렇습니다. 만약 어떤 이유로든 LLM을 실제 서비스에 쓸 수 없다면, 맞춤형 NLP 모델을 학습시키는 것 같은 과제에 LLM을 활용하는 것을 고려해 보세요. 빠른 프롬프트 엔지니어링을 바탕으로 초벌 주석을 달아서, 데이터 주석 작업의 효율을 높이는 데 LLM을 쓰는 것입니다.

### 요약

이 장에서 다룬 핵심을 정리하면 다음과 같습니다.

- 비정형 텍스트 데이터로부터 지식 그래프를 만들려면, 도메인에 특화된 맞춤형 개체명과 그 사이의 관계를 찾아내야 합니다.
- 전통적 NLP에서는 개체명 인식, 관계 추출, 상호참조 해소 같은 여러 모델을 학습시켜 복잡한 작업 흐름으로 엮어야 합니다. 이 학습에는 품질 높은, 사람이 주석을 단 학습 데이터셋을 만드는 데 드는 큰 초기 투자가 필요하고, 모델을 학습·평가·배포·감시하는 데 필요한 전문화된 데이터 과학 기술도 필요합니다.
- OpenAI의 GPT 같은 LLM은, 반복적인 프롬프트 엔지니어링(또는 파인튜닝)을 통해 별다른 손질 없이도 곧바로 활용해, 정확하고 도메인 특화된 지식 그래프를 전통적 NLP보다 훨씬 낮은 초기 비용으로 만들 수 있습니다.
- 전통적 NLP와 LLM은 각자의 장단점이 있으며, 이는 구체적인 도메인과 비즈니스 고려 사항에 따라 달라집니다. 둘은 나란히 공존할 수도 있고, 하나를 써서 다른 하나를 위한 학습 데이터셋을 준비할 수도 있습니다.
- LLM의 생성적 특성 덕분에, 우리는 개체 정규화와 해소가 거의 필요 없이 더 깨끗하고 정확한 지식 그래프를 얻습니다.

## 핵심 용어 해설

| 용어 | 쉬운 설명 |
|------|----------|
| **지식 그래프 (Knowledge Graph, KG)** | 흩어져 있던 정보를 개체(점)와 관계(선)로 연결해 정리한, 검증 가능한 지식 구조 |
| **대규모 언어 모델 (LLM)** | ChatGPT처럼 방대한 텍스트로 학습해 자연어를 이해하고 생성하는 거대한 AI 모델 |
| **비정형 데이터 (unstructured data)** | 이메일·문서·기사처럼 표로 정리되지 않은, 자연어 형태의 데이터 |
| **자연어 처리 (NLP)** | 컴퓨터가 사람의 언어를 이해하고 다루게 하는 기술 분야 |
| **개체명 인식 (NER)** | 텍스트에서 사람·장소·조직 등 개체명 언급을 찾아 정해진 범주로 분류하는 작업 |
| **관계 추출 (RE)** | 텍스트 속 개체 쌍 사이의 의미적 관계를 찾아내는 작업 |
| **상호참조 해소 (coreference resolution)** | "Mayer", "he"처럼 같은 대상을 가리키는 여러 표현을 하나로 이어 주는 작업 |
| **개체 해소 (entity resolution)** | 서로 다르게 표기된 개체가 실제로 같은 대상인지 판별해 통합하는 작업 |
| **중의성 해소 (disambiguation)** | 같은 이름이 가리킬 수 있는 여러 대상 중 실제로 어떤 것인지 가려내는 작업 |
| **트랜스포머 (Transformer)** | 오늘날 LLM의 바탕이 되는 신경망 구조 |
| **전이 학습 (transfer learning)** | 일반 과제에서 배운 패턴·지식을 다른 과제에 재사용하는 학습 방식 |
| **프롬프트 (prompt)** | 모델에게 과제를 표현해 전달하는 입력 텍스트 |
| **프롬프트 엔지니어링 (prompt engineering)** | 가장 성능 좋은 프롬프트를 찾아가는 반복적 개선 과정 |
| **파인튜닝 (fine-tuning)** | 사전학습된 모델을 특정 도메인 데이터로 추가 학습시켜 특화시키는 작업 |
| **환각 (hallucination)** | 근거가 없는데도 모델이 사실을 지어내고 잘못된 추론을 하는 현상 |
| **온도 (temperature)** | 출력의 다양성·창의성을 조절하는 파라미터. 높으면 다채롭고, 낮으면 결정적 |
| **제로샷 / 원샷 학습 (zero-shot / one-shot learning)** | 예시 없이(제로샷) 또는 예시 하나만(원샷) 주고 과제를 시키는 방식 |
| **정규화 (normalization)** | 의미가 같은 개체·관계를 일관된 라벨로 통일하는 작업 |
| **예측 안정성 (prediction stability)** | 같은 입력에 같은 프롬프트를 돌릴 때 결과가 일관되게 나오는 정도 |
| **정밀도·재현율·F1 (precision, recall, F1)** | 예측 품질을 재는 지표. 정밀도=맞은 비율, 재현율=빠짐없이 찾은 비율, F1=둘의 종합 |
| **온프레미스 (on-premises)** | 클라우드가 아니라 자체 서버·설비에 직접 구축·운영하는 배포 방식 |
| **프로그램 담당관 (program officer)** | 연구비를 줄 만한 연구 영역을 찾아내 지원 결정을 이끄는 재단 담당자 |
